## D4.5A cancel contract and frontend policy (2026-09-17)

`DynamicQrResource` declares `@RequestMapping("/dynamic-qrs")` plus `@PostMapping("cancel/{pkey}")`, accepts only `@PathVariable String pkey`, and returns HTTP 200 with `QrHubResponseDTO<Void>`. `SecurityConfig` maps `/dynamic-qrs/cancel/{pkey}` to `CANCEL_PAYMENT`. There is no request body, reason, terminal ID, amount, merchant ID or status argument. `DynamicQrServiceImpl.cancelTransactionQr` returns a builder with `success(true)` and no data value, hence Java `data=null`. The exact deployed JSON representation of that null has not been observed; D4.5B decoder must require the verified success envelope semantics and must not accept an arbitrary JSON 200. If the wire omits `data` under deployed serialization, obtain a sanitized response or serializer evidence before enabling that variant.

The service first checks current-user ownership through `findByPkey(pkey,userId)`, sends `{extId:pkey}` to Core `/partner/transaction-qr/cancel`, invokes `res.throwIfFailed()`, writes local `status_code=20`, then pushes P5 notification. Neither this method nor the checked repository path guards the *old* QR status. The repository's `status_code=0` active check belongs to **create** terminal validation and is not cancel eligibility evidence. Core's allowed states and duplicate-call semantics are not established here. There is no idempotency key, retry instruction, or proven repeated-POST outcome. Core success followed by local update or notification failure can produce a partial result. `CANCEL_ELIGIBILITY`, `CANCEL_IDEMPOTENCY` and `CANCEL_PARTIAL_OUTCOME` remain separate backend/Core gaps; production live submit stays closed.

D4.5B policy: require `dynamicQr.cancel` (`CANCEL_PAYMENT`) independently of create/export/dashboard/static grants. List-row context may require list read, but read permission does not imply cancel authority. Gate on both current permission and an explicit contract-approved eligibility policy; no numeric status alone enables cancel, including 0 or 10, and unknown status never dispatches. Show an explicit confirmation with the QR pkey and a warning that payment availability may change; do not claim irreversibility. Before dispatch, session preparation may refresh; after dispatch, never replay automatically on 401, timeout, abort or transport loss. Distinguish `confirmed`, proven business `rejected`, `not-sent`, dispatched `unknown`, and `stale`. A malformed success body after dispatch is `unknown`. Unknown UX: “So‘rov serverga yetgan bo‘lishi mumkin. Bekor qilish holati noma’lum. Qayta yuborishdan oldin ro‘yxatni yangilab holatni tekshiring; takroriy so‘rov xavfsizligi tasdiqlanmagan.” No immediate blind retry; a second request requires a fresh explicit intent after recheck and established eligibility.

D4.5B implementation boundary: `cancel-qr.ts` decodes only an injected response with `ok=true`, HTTP `200`, envelope `success===true`, and an **explicit** `data:null`. Any malformed/dispatched response is `unknown`. A typed fake port may return a separate `business-rejection` variant; the controller converts it to fixed sanitized text. `SafeApiError.business` alone does not prove a deployed cancel rejection, so no live error mapping exists. `productionCancelGate` has no eligible row and no port. The real list continues to show only the blocked notice to cancel grantees. `CancelQrConfirmation` and the controller are fake-port test surfaces; no production cancel transport or row action is registered. The user's post-D4.5B command gate passed (295/295 tests, 44/44 files; lint/typecheck/build PASS). D4.5 is complete at the frontend command gate; live cancel remains contract-blocked.

Never optimistically set a row to cancelled. After confirmed success only, invalidate current-scope dynamic-list and dashboard keys for which current permissions exist, following `create-invalidation.ts`/`invalidateAfterConfirmed` behavior. A refetch failure is separate from confirmed action and does not invent a row status. Scope or permission loss suppresses late UI/current-scope effects. The existing `one-dispatch-action.ts` catches all dispatch errors as `unknown`; the fake port's explicit rejection result stays separate from thrown transport uncertainty. A future live adapter requires source-grounded rejection evidence.

Static QR page request supports optional `merchantId`, `terminalId`, `regionId`, `districtId`, `search` and defaults `page=0,size=10`. Day 04 minimal UI sends only terminal/page/size; search is absent from the UI. The repository predicate for a future search is `q.id ILIKE :search`. SQL orders by `q.created_at DESC` and scopes to active user-terminal assignments. `StaticQrDTO` fields include string `id`, terminal/merchant names, integer `status`, `link`, `redirectUrl`, optional amount/region/district and offsetless timestamps. Source does not establish whether `link` or `redirectUrl` is the canonical QR payload, nor static min/max units or status meanings. The supported list is complete; preview and those fields remain gated pending evidence.
