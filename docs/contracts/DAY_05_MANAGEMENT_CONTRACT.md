## Terminal list — SOURCE_CONFIRMED, with D5-01 caveat

`TerminalDTO`: `pkey: String` (identifier), `name: String`, `status: Integer`, `merchantId: Long`, `merchantName: String`, `bankAccountId: Long`, `bankAccountName: String`, `mccCode: String`, `terminalType: String`, `districtId: Long`, `districtName: String`, `regionId: Long`, `regionName: String`, `address: String`, `staticQrId: String`, `staticQrLink: String`, `phones: List<String>`, `createdAt/updatedAt: LocalDateTime`. `TerminalRepositoryImpl.FROM` requires the selected user's active (`jut.status=0`) terminal relationship, joins merchant and bank account, and optionally filters IDs. It does **not** require terminal status 0. Search checks only `t.name` and `t.pkey`; order `t.created_at DESC` without tie-breaker. Region is derived from district. Mapper uses `getLong` for numeric joined IDs without `wasNull()`: nullable district/region may emerge as `0`, not reliably null. `phones` is a one-element list of the selected user's phone or `""`. A read UI can omit phone, static QR fields, MCC, dates, address and region/district; it must not infer QR behavior from `staticQrLink`. `terminalType` is raw text; no semantic label was established. Name and linked merchant/bank fields come from inner joins, while optional joined location/static QR/address/date fields can be absent. DTO declarations have no non-null annotations; validate essential identity/display fields at the frontend boundary and treat optional presentation fields defensively.

The list left-joins static QRs while count does not; without a proven uniqueness constraint, a terminal with multiple static QR rows may duplicate and disturb pagination (D5-01). `status` is numeric, but no terminal status label table was proven. The dropdown's `t.status=0` establishes selectability there, not a complete list-status vocabulary.

## Cashier list and membership coverage — SOURCE_CONFIRMED

`CashierDTO`: `id: Long`, `fullname: String`, `phone: String`, `status: Integer`, `role: String`, `terminals: List<CashierTerminalDto>`, `createdAt/updatedAt: LocalDateTime`. Nested `CashierTerminalDto` is `terminalId: String`, `terminalName: String`, `status: Integer`. Main `FIND_ALL` joins user/terminal/merchant/role, requires `m.owner_id = current user`, `r.name='ROLE_MERCHANT_USER'`, optional merchant and terminal filters, and does **not** filter `jut.status` or `u.status`. Search checks only `u.fullname`, `u.phone`; order `u.created_at DESC` with no tie-breaker; `COUNT(DISTINCT u.id)`.

The second query obtains **all active** (`jut.status=0`) terminal relationships for page user IDs under `m.owner_id = ownerId`, ordered `t.name`, without reapplying the merchant/terminal filters. Thus nested terminals are complete *active, owner-scoped* memberships for each returned user, not just the filter/join subset; they exclude inactive and other-owner relationships. Crucially the first query can include a cashier because of an **inactive** matching relationship, while the nested array is empty or lacks that terminal. Do not claim the list filter proves active membership. Role is display text from the DB join, never authorization; only exact get-me permissions authorize actions. Empty array is materialized when the second query finds no rows. Optional dates can be omitted from UI; nullable/unexpected phone/name/role need defensive handling rather than invented values. Status and nested status are numeric; nested returned rows are status 0 by predicate, but full cashier status semantics are unproven. D5-02 tracks the filter discrepancy.

## Assign — ADDITIVE, SOURCE_CONFIRMED / SOURCE_PARTIAL failure outcome

`AssignTerminalRequest`: `cashierId: Long @NotNull`, `terminalIds: List<String> @NotEmpty`, each `@NotBlank`; no merchant ID, replacement flag or unique-element rule. Service verifies `isCashierOwner`: cashier has at least one relationship through a terminal whose merchant owner matches current user and DB role `ROLE_MERCHANT_USER` (no active relationship predicate). `isTerminalsOwner` requires count of current user's **active** terminal joins equal to supplied list length. Repository loops each ID and executes `INSERT ... ON CONFLICT (user_id,terminal_id) DO UPDATE SET status=0, updated_at=now()`. No deletion or clearing of other pairs: **ADDITIVE**, existing active pairs remain, inactive same pair reactivates, already-active pair updates timestamp. Duplicate IDs can fail ownership count; no explicit idempotency key/retry guarantee.

Unlike create, assign has no `@Transactional` at the service method. The per-ID updates are separate JDBC calls; if a later update fails, earlier writes may persist. Controller HTTP 200, builder `success=true`, unset `Void data`; the same D5.4B shared DTO/Jackson source-level evidence supports explicit `"data":null`, not omitted data, without proving deployed serialization. D5.5A sends one bulk `{cashierId: number, terminalIds: string[]}` request only from the current scoped cashier row and currently valid terminal lookup. The frontend excludes ACTIVE memberships from choices and blocks any selected ID that becomes active before dispatch; inactive relationships are not inferred and may be reactivated by the backend. One intent makes at most one POST, with no automatic replay or optimistic membership insertion. Confirmed explicit-null success invalidates every current-scope cashier-list variant; failed refetch does not downgrade confirmation. A dispatched ambiguous outcome is UNKNOWN: none, some, or all IDs may have applied, so a fresh membership read and a new explicit intent are required. The live client has no source-proven business-error classifier and does not map arbitrary errors to REJECTED. D5-03 and D5-04 remain OPEN; no staging outcome is claimed.

## ID and wire safety, status, ordering, nullability

Java `Long` IDs in list rows, query parameters and cashier assign/create-generated internals may serialize as JSON numbers beyond JavaScript's safe integer range. Require safe integral numeric wire IDs before converting to canonical decimal strings; reject unsafe numeric IDs rather than silently rounding. Dropdown merchant/bank IDs are already decimal **strings** from `CAST(... AS varchar)`; validate decimal form and preserve value. Terminal `pkey`/terminal lookup ID/terminalIds/unassign terminalId are **strings**, not Java Long; do not force a guessed hex format or numeric conversion. `totalElements` is also Long and needs safe-count handling. Account/MFO/TIN/contract are exact text. No Java DTO here marks per-field nullability; SQL joins, mapper behavior and request validation above support the stated guarantees only. `LocalDateTime` serialization shape and null policy require defensive decoding if displayed. For status, only SQL's `0` selectable and relationship `0` active / `1` removed are evidenced; no complete terminal/bank/cashier code-to-label table. Unknown status remains neutral. `terminalType` has no proven semantic mapping. Equal-time terminal/cashier ordering is unstable; bank uses descending ID. All page offsets are `page * size`, and no stable secondary ordering is supplied.
